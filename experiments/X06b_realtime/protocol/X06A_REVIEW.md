## 2. 未达标项一：切句损失 −0.045（门槛 −0.03）

审查者拆解（`reviewer_audit/x06a_s2_audit.py`，FMH，最短静音 0.4 秒，H3）：

- 50% 的真值句落在"一段 VAD 覆盖多句"的段里，6% 被切成多段，43% 一对一。
- **损失几乎全部来自合并和切碎**：把这些句子换回正确切句的结果后，R90 F1 为 0.663，与正确切句的 0.661 持平；一对一的句子 VAD 反而略好（准确率 0.778 对 0.755）。
- 合并由间隔长度决定：0.3–0.6 秒的间隔 92% 被连起来，0.6–0.9 秒 26%，0.9 秒以上几乎为 0。噪声水平影响很小（最低与最高四分位分别为 28% 和 35%）。

**原因是模拟流的设计（reviewer 的问题）。** 同一说话人相邻的两句，在原始对话中间隔着对方的发言，情绪也常常已经变了。模拟流把它们直接拼在 0.3–1.5 秒的间隔里，等于制造了大量"情绪不同、却紧挨着"的句对。这会高估真实单人场景下的切句损失。X06b 改用按原始对话时序构造的流重测，0.03 的门槛不变；原拼接流的结果保留，作为"停顿很短"情况下的最坏参考。

## 3. 未达标项二：内存增长 127%（门槛 10%）

H3 回放的墙钟是媒体时长的 1.36 倍，输入积压中位数 529 秒，最大约 20 分钟。协议要求不丢帧，所以积压的帧会一直留在内存里。H_ref 单条流的积压更大（中位数 691 秒），内存增长也更大（234%），方向一致。**内存增长很可能是积压的结果，而不是泄漏。** X06b 消除积压后重测；若积压消失而内存仍增长，再按泄漏排查。

## 4. 最重要的发现：跟不上实时

- 单看从 VAD 判定结束到输出，H3 的延迟 P50 为 1.59 秒；但用户感受到的是"从说完话到出结果"，这个数的 P50 是 531 秒，因为输入一直在积压。
- 瓶颈在生产者：人脸检测累计 8,768 秒，视频解码 4,136 秒，而媒体只有 10,755 秒，两者加起来就超过实时。
- 端点之后的处理约 1.6 秒，其中轨迹关联、排序、裁剪与 Q 输入构造占 0.85 秒，Q-AV 占 0.55 秒，A3 与 V2 各约 0.05 秒。
- H_ref 比 H3 慢约 0.39 秒（单条流，仅作参考）。

## 5. 其他记录

- 0.4 秒最短静音在 AISHELL-4 test 上没有单独评估，X06b 补测（只用 CPU）。
